## 4. Feature deep-dive (with code references)

### 4.1 Signup with OTP — [server/controllers/Auth.jsx](server/controllers/Auth.jsx)
1. `POST /sendOtp` → checks email isn't already registered → generates a 6-digit numeric OTP (`otp-generator`) → saves an `OTP` document.
2. A Mongoose **pre-save hook** on the OTP model emails the OTP to the user — [server/models/OTP.jsx](server/models/OTP.jsx). *(Nice talking point: the email side-effect lives in the model layer via a lifecycle hook.)*
3. `POST /signUp` → validates all fields → fetches the **most recent** OTP for that email (`.sort({_id:-1}).limit(1)`) → compares → if OK, **bcrypt-hashes** the password (10 salt rounds) and creates the `User`.
4. A post-save hook on `User` sends a welcome email.

> ⚠️ **Know this weakness:** the **OTP-expiry check is commented out** (lines ~131–136). So OTPs never expire — a real security gap. Great "what I'd fix" item: add a TTL or an explicit `createdAt + 10 min` check (you even left the code for it).

### 4.2 Login & JWT — `login` in [server/controllers/Auth.jsx](server/controllers/Auth.jsx)
- Looks up user, `bcrypt.compare(password, hash)`.
- Signs a JWT with payload `{email, _id, role, district, name}`, **expires in 3h**.
- Sends it **three ways**: as a `Set-Cookie` (`token`), in the `Authorization` header, and in the JSON body. The cookie options are `secure:true, sameSite:'none', httpOnly:false`.

> ⚠️ **`httpOnly:false`** means JavaScript can read the cookie → vulnerable to **XSS token theft**. Omnissa is a security company; *flag this yourself*: "I'd set `httpOnly:true` so the token isn't reachable from JS." Big credibility win.

### 4.3 Create post — `createPost` in [server/controllers/Posts.jsx](server/controllers/Posts.jsx)
- Verifies JWT → enforces **one post per day per user** (checks if a `DonorPosts`/`ReceiverPosts` doc already exists for that email).
- Validates the uploaded image's extension (`jpg/jpeg/png`) and uploads to Cloudinary.
- Creates a `Post`, then a `DonorPosts` or `ReceiverPosts` pointer doc based on `role`.
- `Post.expiresAt` is computed to **next 7 AM** (see [server/models/POST.jsx](server/models/POST.jsx)).

### 4.4 The matching algorithm — `connectedPosts` in [server/controllers/ConnectedPosts.jsx](server/controllers/ConnectedPosts.jsx) ⭐
This is the heart of the app. Route is guarded by the **`isDonor`** middleware (only donors can donate).
1. Verify JWT → find the donor's post.
2. Find the receiver's post (`reciverPostId` from body).
3. **Rule 1:** `receiver.quantity <= donor.quantity` (donor must have enough food).
4. **Rule 2:** `donor.district === receiver.district` (same district only).
5. Mark both posts `status:true` and set `connectedTo` to each other.
6. Delete both from the `DonorPosts`/`ReceiverPosts` "active" pools.
7. Create a `ConnectedPosts` record linking both.
8. **Email both parties** each other's name, email, and phone, so they can coordinate.

> ⚠️ **Atomicity weakness (great DBMS talking point):** steps 5–8 are **multiple independent writes with no transaction**. If the server crashes after deleting the donor post but before creating the `ConnectedPosts` record, you get **inconsistent state**. In a relational DB you'd wrap this in a transaction; in MongoDB you'd use a **multi-document transaction** (replica set) or design for idempotency.

### 4.5 Daily cleanup — `BootUp` in [server/controllers/Bootup.jsx](server/controllers/Bootup.jsx)
- `GET /BootUp` loops over **all** donor posts, receiver posts, and connected posts, deleting any where `expiresAt < now` **or** `status == true`.
- It's called from the **frontend on page load** (see the reload logic in [client/src/App.jsx](client/src/App.jsx)).

> ⚠️ **Two weaknesses worth raising:**
> 1. **N+1 / O(n) deletes:** it fetches all posts, then deletes one-by-one in a loop → many round-trips. Better: a single `deleteMany({ $or: [{expiresAt:{$lt:now}}, {status:true}] })`, or a **MongoDB TTL index** that auto-deletes expired docs with zero code.
> 2. **Cleanup triggered by a client** is unreliable (only runs if someone visits). Proper fix: a **cron job / scheduled task** (e.g. node-cron, a Vercel Cron, or a TTL index). This is a textbook "move work off the request path" answer.

### 4.6 Likes — `likePost`
- Toggles the user's `_id` in the post's `likes` array using `$push` / `$pull`. Simple, atomic at the single-document level.

## 5. Data model (7 collections)

| Collection | Key fields | Purpose |
| --- | --- | --- |
| **User** | firstName, email, phoneNo, password (hashed), role `['Donor','Reciever']`, district (enum of ~700 Indian districts), posts[] | Account + identity |
| **Post** | email, title, description, imageUrl, quantity, district, status, `expiresAt` (next 7 AM), `connectedTo`, likes[] | A single food post |
| **DonorPosts** | email, posts (ref→Post) | "Active donor pool" pointer |
| **ReceiverPosts** | email, posts (ref→Post) | "Active receiver pool" pointer |
| **ConnectedPosts** | donorEmail, receiverEmail, donorPost, receiverPost, expiresAt, likes[] | A completed match |
| **OTP** / **ForgotPassOtp** | email, otp, createdAt | Email-verification codes |

- **Relationships** use `ObjectId` refs + Mongoose **`.populate()`** (the NoSQL equivalent of a SQL JOIN, done app-side).
- **Why separate DonorPosts/ReceiverPosts pointer collections?** They act as small "index/queue" tables of *currently active* posts, so listing/cleanup doesn't scan the whole `Post` collection. (You can defend it as a denormalization-for-read-speed choice — or admit a compound index on `Post` could replace them.)

## 6. Security deep-dive (Omnissa will dig here — own it)

| Area | What you did | What you'd improve |
| --- | --- | --- |
| Passwords | bcrypt, 10 salt rounds (slow hash + per-password salt → defeats rainbow tables) | Fine; could bump cost factor over time. |
| Auth token | JWT, 3h expiry, HMAC-signed with `JWT_SECRET` | Add **refresh tokens**; rotate secrets; shorter access-token TTL. |
| Cookie | `secure:true`, `sameSite:'none'` | **`httpOnly:true`** (currently false → XSS-readable). |
| OTP | random 6-digit, emailed | **Re-enable expiry**; add attempt **rate-limiting** (brute-force a 6-digit code is only 10⁶ tries). |
| Authorization | `isDonor` middleware checks `role` from JWT | Centralize role checks; verify on *every* protected route (some controllers re-verify JWT inline instead of using middleware). |
| Transport | HTTPS (Vercel), CORS locked to the frontend origin with `credentials:true` | Good. |
| Secrets | `.env` (DB URL, JWT secret, SMTP, Cloudinary) | Use a secrets manager in production. |

> **Power line:** "Because the token is sent in a cookie *and* the body *and* a header, and the cookie is `httpOnly:false`, the most important hardening I'd do is pick **one** transport — an httpOnly, SameSite cookie — and re-enable OTP expiry plus rate-limiting. For an identity-and-security company like Omnissa, that's the first thing I'd lock down."

## 7. CS fundamentals this project demonstrates (name them out loud)

- **Operating Systems / Concurrency:** Node's **single-threaded event loop** + **non-blocking async I/O** lets one process handle many concurrent requests while waiting on DB/email/network. `async/await` is syntactic sugar over Promises (the microtask queue). *(Compare to Java's thread-per-request model — Omnissa loves this contrast.)*
- **Networking:** REST over HTTP; proper **status codes** (200/400/401/403); **CORS** preflight + `credentials`; **cookies vs Authorization header**; stateless auth via JWT.
- **DBMS:** schema design, **indexing** (`_id` is auto-indexed; you sort by it), **references + population** (= JOIN), **transactions/atomicity** (the gap in §4.4), **TTL** as a cleanup primitive.
- **DSA:** the matching is an O(1) lookup + comparison per donation; `BootUp` is O(n); likes toggle is a set membership check (`includes` is O(n) on the array — could be a Set).
- **OOP / design patterns:** Mongoose **models** = classes; **middleware** = chain-of-responsibility / interceptor pattern; **lifecycle hooks** (pre/post save) = observer pattern; MVC-ish separation (routes → controllers → models).

1. **Re-enable OTP expiry + add rate-limiting** (security).

## 9. Scalability / system design (be ready for "how would this handle 1M users?")

- **Stateless API** → run **N Express instances behind a load balancer**; JWT means no server-side session, so any instance can serve any request. *(This statelessness is exactly why JWT was a good call — say that.)*
- **Database:** add **indexes** on `email`, `district`, `status`; use **compound index** `(district, status)` to make matching/listing fast; **shard** by district or region if needed.
- **Reads:** cache hot lists (active posts per district) in **Redis**; serve images via Cloudinary's **CDN** (already do).
- **Background work:** move email sending and cleanup **off the request path** into a **queue** (e.g. Bull/RabbitMQ) + workers, and a **scheduler** for daily expiry — so a slow SMTP server never blocks a user response.
- **Matching at scale:** index posts by district so finding candidate receivers is a fast indexed query, not a scan.

**Q1. Tell me about this project / walk me through it.**

## 12. Deep code-level Q&A (bonus — only if the interviewer goes technical)

> Use these if the interviewer digs into implementation. For most rounds, §11 is enough.

**Q1. Walk me through what happens, end to end, when a donor donates to a receiver.**
> Donor clicks Donate → frontend `POST /connectedPosts` with the receiver's post id and the JWT cookie → `isDonor` middleware verifies the token and checks `role==='Donor'` → controller loads both posts → checks **quantity** (donor ≥ receiver) and **district** (must match) → marks both posts `status:true`, links them via `connectedTo` → removes them from the active donor/receiver pools → creates a `ConnectedPosts` record → emails both parties each other's contact details → returns success. The UI then shows the match on the Connected Posts page.

**Q2. Why JWT instead of server-side sessions?**
> JWT is **stateless** — the token itself carries the identity (signed, tamper-evident), so I don't store sessions server-side. That lets the API scale horizontally: any instance behind a load balancer can validate any request with just the secret. Trade-off: you can't easily **revoke** a JWT before it expires, which is why I keep the TTL short (3h) and would add refresh tokens.

**Q3. How is a password stored, and why bcrypt specifically?**
> bcrypt with 10 salt rounds. bcrypt is a **deliberately slow** adaptive hash with a **built-in per-password salt**, so identical passwords hash differently (defeats rainbow tables) and brute-forcing is expensive. The cost factor can be raised as hardware gets faster. I never store or log the plaintext.

**Q4. I see the OTP never expires in your code. Is that a problem?**
> Yes — that's a real bug; the expiry check is commented out. An OTP that lives forever widens the window for interception/replay. I'd re-enable a 10-minute expiry (ideally a **TTL index** so MongoDB auto-deletes it) and add **rate-limiting** on verification, since a 6-digit code is only 10⁶ possibilities and is brute-forceable without throttling. *(Volunteering this shows security maturity.)*

**Q5. Your donation does several DB writes with no transaction. What can go wrong?**
> If the process crashes mid-way — say after deleting the donor's active post but before creating the `ConnectedPosts` record — the data is **inconsistent** (post gone, no match recorded). The fix is a **multi-document transaction** (MongoDB supports them on replica sets) so the writes are all-or-nothing, or making the operation **idempotent** so it can be safely retried.

**Q6. The `BootUp` cleanup fetches all posts and deletes them in a loop. Critique it.**
> Two issues. First, it's **O(n) with one round-trip per delete** — an N+1 pattern; a single `deleteMany` with an `$or` filter, or a **TTL index**, would do it in one shot. Second, it's **triggered by the client on page load**, so cleanup only happens if someone visits — unreliable. I'd move it to a **scheduled cron job** or let a TTL index handle expiry automatically. That removes work from the request path entirely.

**Q7. What's a TTL index and how would it help here?**
> A **TTL (time-to-live) index** in MongoDB lets you mark a date field so the DB **automatically deletes** documents a set time after that timestamp — a background thread does it. My posts already have `expiresAt`, so a TTL index would delete expired posts with **zero application code** and no cron job. (Caveat: TTL runs ~once a minute, so deletion isn't instant.)

**Q8. How does authorization work — how do you stop a receiver from donating?**
> The donate route is wrapped in the `isDonor` middleware, which verifies the JWT and checks the `role` claim equals `'Donor'`, returning 400/403 otherwise. Middleware is the **interceptor pattern** — auth runs before the controller, keeping the check in one place. *(I'd standardize this; a few controllers re-verify the JWT inline instead of using the middleware, which I'd refactor.)*

**Q9. Why MongoDB and not SQL? Would you choose differently now?**
> I chose MongoDB for **schema flexibility** while iterating and because posts/users are naturally document-shaped. But the matching feature is **relational and transactional**, which is SQL's strength. Knowing what I know now, I'd seriously consider Postgres for the safety of foreign keys + ACID transactions, or at least lean on MongoDB's transaction support for the match.

**Q10. What is `.populate()` and how does it relate to SQL?**
> Documents store **ObjectId references** to other documents (like foreign keys). `.populate()` tells Mongoose to fetch and substitute the referenced documents — effectively an **application-side JOIN**. It's convenient but can cause extra queries, so for hot paths I'd watch for over-fetching.

**Q11. What is CORS and how did you configure it?**
> CORS is the browser's **same-origin protection**: a page can't call a different origin's API unless that API opts in via `Access-Control-Allow-*` headers. My Express server sets the allowed **origin** to the frontend URL and `credentials:true` so cookies are sent cross-origin. Without it, the browser blocks the request even though the server would have answered.

**Q12. Cookie vs Authorization header — you use both. Which is better?**
> A cookie is sent automatically and, if `httpOnly`, is **safe from JS/XSS** but needs CSRF protection. An `Authorization: Bearer` header is immune to CSRF but must be stored somewhere JS can reach (XSS-exposed). Sending the token **three ways** (cookie + header + body) like I do is redundant and increases attack surface — I'd pick **one**: an httpOnly, SameSite cookie, plus CSRF tokens.

**Q13. How does Node handle many concurrent requests on one thread?**
> Node uses a **single-threaded event loop** with **non-blocking I/O**. When a request waits on the DB or email, Node doesn't block — it registers a callback and serves other requests; when the I/O completes, the callback (a microtask via Promises/async-await) runs. So it's great for **I/O-bound** workloads like this. CPU-bound work would block the loop — for that you'd use worker threads or a separate service.

**Q14. There are no tests. How would you start testing this?**
> I'd start where bugs are costly and logic is pure: the **matching rules** (quantity ≥, same district) as unit tests, and **auth** (signup/login/OTP) as integration tests with an in-memory Mongo. Then API tests with supertest for the main routes. The matching function is the highest-value target because it's the core business rule.

**Q15. How would you scale this to a million users?**
> Stateless API behind a **load balancer** with many instances (JWT makes that easy); **indexes** on email/district/status and a compound `(district,status)` index for matching; **Redis cache** for hot per-district post lists; images via **CDN** (already Cloudinary); and move **email + cleanup to a queue + scheduler** so they're off the request path. If a single DB is the bottleneck, shard by region/district.

**Q16. What was the hardest bug or design problem you faced?**
> *(Use a real one. A strong honest answer:)* Getting cross-origin **cookie auth** to work — the cookie wasn't being stored until I set `sameSite:'none'` + `secure:true` and `credentials:true` on both axios and CORS. Debugging it taught me how browsers treat third-party cookies, which is exactly the kind of client–server detail that matters for secure web apps.

**Q17. Where do side-effects like emails live, and is that a good idea?**
> Emails are sent from **Mongoose lifecycle hooks** (e.g. OTP/User `pre`/`post('save')`) — the **observer pattern**. It's elegant (the model "announces" events) but couples persistence to email and makes failures hard to handle (a failed email shouldn't fail the save). At scale I'd emit an event to a **message queue** and let a worker send mail, decoupling the two.

**Q18. If you rebuilt this for an enterprise like Omnissa, what would change?**
> Stronger **identity**: httpOnly cookies, OTP expiry + rate-limiting, refresh tokens, maybe SSO/OAuth. **Reliability**: transactions for the match, a scheduler for cleanup, a queue for email. **Observability**: structured logging, metrics, tracing. **Tests + CI**. And I'd write it in **Java/Spring** with the same architecture — controllers, repositories, an auth filter, entities.
